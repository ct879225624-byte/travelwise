# TravelWise V1.1-C Personal Opportunity Engine

## 数据流与边界

`/`、`/discover`、`/calculate` 保持公共入口；登录后的 `/me` 提供机会、下一步和权益概览。原 V1 工作台原样保留为 `/me/records`，继续执行会员、批次账本、活动、待办、收益和方案管理。

`personalOpportunityEngine` 每次访问按当前记录重新评估，不保存可能过期的“已确认资格”缓存。所有个人读取和修改均先执行 `requireOwner`，所有私人查询显式约束 `ownerId`；提醒刷新、状态修改和条件确认复用 V1 的 Owner 行锁。没有客户端提供身份、权限或收益结果的通道。

只从 CMS 正式表读取 `published`、非 DEMO、`official_verified` 活动，要求官方已核实来源 URL 和核实日期。暂停、归档、结束、未开始、日期不完整的活动不能进入当前机会卡片。只按已保存的会员计划或个人参与记录建立关联。不符合条件的卡片明确是资格核对结果，不作为可参加建议。

雷达事件、监控版本、网页原文、AI 提取任务不参与匹配或权限决策。A/B 的手动审核和发布继续由原管理员流程控制。无 AI Key 时 C 完整运行；没有修改 AI Provider Adapter。

## 规则与个人条件

原 `evaluateQualification` 和 `validateRuleApplicability` 继续负责规则判断，只使用原四态：

| 原状态 | 中文 |
|---|---|
| meets-known-conditions | 符合已知条件，仍以官方核验为准 |
| fails-known-conditions | 不符合已知条件 |
| information-insufficient | 信息不足 |
| rule-pending-verification | 规则待核实 |

管理员在“创建/修订规则”中可填写 `structuredContent.opportunity`，保存为新规则版本。JSON 经严格 Zod 校验；未知字段不接受。不从自然语言推断消费门槛、卡种、报名或入住资格。留空、无效或 `complete:false` 均不能确定为符合。

示例仅说明格式，不是优惠数据：

```json
{
  "complete": true,
  "membershipTiers": ["白金"],
  "cardRequired": true,
  "cardTypes": ["人工核对的适用卡种"],
  "benefitNames": ["早餐"],
  "enrollmentRequired": true,
  "brands": ["人工核对的品牌"],
  "regions": ["人工核对的地区"],
  "channels": ["人工核对的渠道"],
  "usesLimit": 1,
  "minSpendMinor": "10000",
  "minNights": 1,
  "minPoints": "1000",
  "spendEndsAt": "2026-11-01T00:00:00+08:00"
}
```

`complete:true` 必须意味着管理员已将所有影响资格的条款完整核对并录入；现有纯文本规则不会被自动升级。各关联规则分别验证，限制范围不以集合并集放宽。金额为整数字符串（分），积分为整数字符串；不经浮点货币运算。

会员等级、到期、卡种与未使用权益来自 V1 wallet；已登记参与状态提供报名事实；个人填写的品牌、渠道、消费、晚数、入住日期和次数保存在 `opportunity_profiles`。积分条件只使用现有积分批次，不包括预计奖励。过期等级、权益和积分不能满足条件。

对资格、奖励、时间、规则正文、结构化条件、版本和核实状态计算稳定 SHA-256 指纹，排除活动标题等展示修改。首次评估保存基准（`confirmedAt=NULL`），人工确认才写确认时间。已发布有效内容变化后旧事实停止复用，原四态降为待确认并生成一次规则核对提醒。确认请求携带旧指纹时拒绝；不自动改写旧规则或旧计算方案。

## 排序和收益

| 原因 | 分值 |
|---|---:|
| 符合已知条件 | 100 |
| 3 天内截止 / 14 天内截止 | 30 / 20（二选一） |
| 有可复算方案 | 15 |
| 已登记相关会员 | 10 |
| 明确下一步 | 5 |

同分依次按下一截止时间、活动 ID 排序，每张卡片展示分项。筛选支持四态资格、会员、截止窗口和可计算性；价值排序把未知排在最后，不把未知当零收益。

三类原计算器保持算法和精度不变。保存方案时服务端记录当前机会指纹；机会只复算指纹及关联规则一致、输入完整、来源和报价时间明确、资格满足的方案。读取时再次调用现有三个纯函数，忽略客户端保存的结果金额。展示原始输入、来源、假设、公式和风险；缺少金额、估值、报价或依据时显示“收益待计算”。

房价/优惠比较显示“潜在节省”；活动回报显示“预计返还”（扣除填写的增量成本的估计净价值）；实际收益继续读取原 `reward_records.kind=realized`，预计积分不会进入余额或实际现金收益。固定积分以正式活动奖励数量核对，三类结果均不产生积分流水或兑现记录。

## 提醒和时区

`generateReminders` 是纯函数，真实日期驱动：报名、结构化消费截止、入住截止、领取开始/截止、个人领取日期、积分批次到期、待办临近/逾期、规则变化。预订截止不会被伪装成消费截止。未知日期不会推断，未确认的待办日期不会触发自动提醒。活动结束后保留真实的个人待领取提醒。

默认报名/消费/入住/领取提前 14×24 小时，积分提前 30×24 小时，待办提前 7×24 小时。截止和有效区间使用实际 ISO instant：开始包含，结束排除，等于截止即为到期/逾期。规则和活动显示各自 IANA 时区，个人批次和待办显示香港时间，所有计算不依赖服务器本地时区。稍后时间必须在未来 90 天内，界面提供稍后一天。

唯一键 `(owner_id, source_key)`：业务来源 ID + 事件类型 + 真实截止时间；规则事件使用内容指纹。键不含“今天”，并发访问或跨日不产生新通知。同步只更新内容/适用性，保留已读、完成、忽略和稍后状态；过期稍后恢复待处理而不创建新行。来源变化或任务完成后 `active=false`，历史保留。完成待办提醒时在同一事务完成原待办；完成提醒不会虚报活动报名、积分到账或奖励实现。

站内提醒在访问 `/me` 或私人机会 API 时更新，没有后台轮询、外部通知、消息队列或缓存基础设施。关闭网站不会发送提醒。

## 迁移和运行

`0008_youthful_forge.sql` 仅增加 `opportunity_profiles`、`personal_reminders`，包含 Owner 外键、用户内唯一约束和状态/稍后日期约束。没有改写 V1 内容、账本、规则历史或 A/B 表，旧版本代码可继续工作。原 `db:migrate` 执行即可；本任务仅在隔离测试库执行，生产迁移未授权。

当前采用 Owner 小数据量实时查询，不引入额外基础设施。后续内容量显著增加时再按当前会员计划收窄候选 SQL 和分页；不提前引入队列或缓存。正式内容、结构化条件、个人记录和报价仍需人工维护，未连接银行/酒店账户验证。
